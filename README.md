# Coparkour

橫向無限跑酷。多人在**同一個畫面**上競速，但**彼此不碰撞**——別人是半透明的貓，只看得到、撞不到。

**整個專案就是一個 Cloudflare Worker。** 前端和 WebSocket 伺服器同源，一行指令部署完就能玩：

```bash
npx wrangler deploy
```

---

## 這一版加了什麼

外觀整套換掉了，設計系統移植自 `frontend-sandbox`（AETHER）。核心判斷是：那個專案裡讓畫面「每次都不一樣」的機制全都很便宜（整數雜湊 ~10 ALU、正弦和 ~24 ALU），貴的是光線行進與逐頂點陰影行進——而那些在解 3D 的問題，我們是 2D，不需要。**所以搬的是設計系統，不是渲染器。**

- **一天的時刻** — `daycycle.js` 一比一移植。房間 seed 決定起始時刻，日夜自己走。每幀約 30 次浮點運算，不畫任何東西，只吐五個數字。
- **天氣** — 房間 seed 決定晴／雨／雪。雨雪是無屬性頂點拉取，零 CPU 狀態、零 buffer。
- **座標整數雜湊** — 裝飾物不再照順序生成，改成綁在格子座標上。無狀態、記憶體不隨距離成長、鏡頭可以往回看，而且**多人一致性是免費的**（同 seed + 同格子 = 同一叢草，伺服器不多傳一個位元組）。
- **clump-and-thin 撒花** — 半徑用 `u` 不是 `sqrt(u)`，再用 `u²·0.92` 往外圍淘汰，所以花叢沒有可見的邊界。每叢一色。
- **蝴蝶與螢火蟲** — 每叢花有 1/2 的機率帶蟲，有的話 1～3 隻機率均等。白天蝴蝶、晚上螢火蟲，黃昏交叉淡入。飛行用脈衝響應的和，不是正弦——見下。
- **四層非諧波山脈 + 空氣透視** — 波長 74/41/23/13 互不成整數比，走多遠都不重複。
- **那隻貓** — 見下一節。
- **Bayer dither** — 深色漸層不再有色帶。
- **遊蕩的 NPC 與重生點** — 每 2000m 住著一隻旅貓，用的是地形驗證那隻 bot 的腦。花金幣可以把牠買下來當重生點。位置一個位元組都不走網路，見〈NPC〉那一節。

## 那隻貓

`assets/cat.bin` 是 `frontend-sandbox` 烘焙出來的 3D 模型：22,405 個頂點、39,328 個三角形、23 根骨頭的**剛體階層**（沒有蒙皮權重，每個頂點屬於一根骨頭），三個花色共用同一份幾何、只換調色盤。

**每一幀都是真的 3D。** 骨架每幀跑一次、姿勢由 `pose.js` 的 `Driver` 連續積分、步頻跟著實際速度走、換方向是真的轉身。看起來像 2D 塗鴉的是**著色**，不是動畫：

- **三階調卡通著色。** 漫射項硬切成三塊平調，邊界只有一個 `fwidth` 寬的 smoothstep（大約一個像素，剛好不鋸齒）。三個色調不是三個無關的常數，而是拿 `daycycle.js` 自己那條式子（`tint × 2.4 × ndl + ambient × 1.5`）在 ndl = 1.0 / 0.24 / 0.035 取三次——所以貓跟平台是被同一盞燈照的，夜裡陰影會自己偏藍。
- **翻面外殼墨線。** `outline` 群組佔 44% 的三角形，就是為這個存在的：用 **front-face culling**，剩下的是外殼背面，被身體擋住、只在輪廓外露出來一圈墨色。

| | |
|---|---|
| 前進軸 | **+Z**（量出來的：頭骨頂點重心 z=+0.571，尾巴 z=−1.221） |
| 每幀 | 1 隻貓 2 個 draw / 39,328 tris；12 隻 24 個 draw / 471,936 tris |
| CPU 姿勢積分 | 12 隻貓 0.18 ms |
| 遮擋 | 每隻貓分到一段 `gl.depthRange`，佇列由遠而近——不用清深度緩衝 |
| 轉身 | 14 rad/s（180° / 224 ms ≈ 13 幀），頭先動、身體再跟 |
| 花色 | `orangin` 橘白、`tabby` 虎斑、`calico` 三花——進遊戲前選，可隨時換 |

### 轉身

換方向不是把貼圖翻面，是真的轉。這是原專案的招牌細節，機制照搬：**貓是先轉頭再轉身**（`HEAD_YAW_MAX = 0.9`——「貓用轉頭看東西，脖子不夠用了身體才跟上」），用的是 rig 本來就有的 `aimYaw` / `aimWeight` 通道，所以 `Sway` 也讀得到，鬍鬚跟尾巴自己會跟著甩。

**永遠從正面轉過去，不會背對玩家**——這件事是用參數化保證的，不是用 if 擋的：ψ = 0 是鼻子朝鏡頭、±π/2 是兩邊側面，夾在 [−π/2, +π/2] 裡。背面在 ±π，結構上就到不了，所以左右狂按只會讓轉到一半的身體反向轉回去，不會轉圈。

原專案的 6.0 rad/s 轉 180° 要 524 ms，對一個一直在換方向的跑酷來說太慢（整段跳躍都朝錯邊），改成 14.0。

做的時候有兩個 bug 是看影格才發現、不是想出來的：身體 64 ms 就到位但脖子要 420 ms 才收回來，於是每次左轉結束都在給玩家看後腦杓——改成夾**存下來的** aim；接著夾在正負 π/2 又讓頭在轉完後正側著、五幀沒有臉——改夾在靜止偏角上。

沒有 LOD，是刻意的：逐骨頭數過，身體 4,472 / 頭 4,408 / 耳 4,256 / 尾 2,148 / 腿 4,672，全都在輪廓上。40 px 下唯一可省的是六根鬍鬚（1.8%），不值得。真正的 LOD 要在載入時做網格簡化，那是另一件事，不該偷偷塞。

**已知的偏離**（`public/src/cat/cat.js` 開頭有完整說明）：`cat.bin` 的描邊群組頂點色是壞的（身體和頭的外殼共用了頂點著色的幾何，5,004 個是墨色、4,554 個是奶油色），照存的畫出來根本沒有描邊，所以整群強制成它自己多數派的墨色；描邊沿法線加厚；靜止時頭仍偏 13° 朝鏡頭（純側面時眼睛是貼在頭骨正面的扁圓片，完全側著就沒有臉）；`air`/`fall`/`wall`/`dead` 是新寫的，原專案沒有跳躍和死亡。改成轉身之後，朝左看到的是模型的**另一側**花紋而不是鏡射，比較忠實但三花會看得出差異。**腳還是會有點打滑**——步頻跟速度成正比，但這副骨架的肩膀只擺 ±0.62 弧度、腳掌移動約 13 px，而地面一個步幅要走 107 px，這是資產本身的振幅給不了的。

測試時抓到兩個 bug：`Sway` 的彈簧鏈在 80 ms 的幀長會炸開（`Driver` 自己夾 dt，`Sway` 沒有），改成切成 ≤10 ms 的子步；頭轉向鏡頭之後遠端那顆眼睛會戳穿嘴邊的墨線。

畫不出貓的裝置（沒有 WebGL2）會退回原本的方塊角色，遊戲照常。

## NPC：位置是時間的函式，不是封包

地圖上每 2000m 住著一隻旅貓。牠用的是 `tools/verify-level.mjs` 那隻地形測試 bot 的腦——那顆腦現在住在 `public/src/bot.js`，兩邊共用，差別只有兩個參數：NPC 走的方向可左可右，而且**沒有二段跳**。

牠會在左右各 4 個落腳點（外加腳下這塊板子的另一端）裡挑一個走過去，到了待機 4 秒再挑下一個；1000m 內有另一隻的話，下一個目標必須在反方向。買下來之後牠就在那塊板子上定居，只左右踱步，再也不跳。

### 難的不是走路，是「大家看到同一隻貓」

伺服器不跑物理（那會讓 Durable Object 永不休眠，免費額度撐不住），也不轉送 NPC 座標（每秒十次乘上每一隻，額度直接爆掉）。所以位置不能用「傳」的，只能用**算**的：

把 NPC 的一生切成固定 6 秒的**時槽**，前 2 秒移動、後 4 秒待機。

- **第 k 槽的落腳點是純幾何函式** `f(seed, 編號, k)`——抽籤的亂數也只由這三個值決定。這條鏈不含物理，重播一小時份只是幾萬次範圍查詢，所以第 50 分鐘才進房的人，從錨點算到現在會得到跟老玩家一樣的答案。
- **那 2 秒的移動才跑真物理**（同一套 `player.js`）。兩台電腦在這 2 秒可能差幾 px，但待機段會把位置收斂回落腳點——誤差不累積，每 6 秒重新對齊一次。
- 伺服器只需要多發一個東西：房間的**世界時鐘原點** `t0`（跟 seed 存在一起，換地形就一起重來）。客戶端用現成的 ping/pong 校正時差。

於是 NPC 的座標**一個位元組都不經過網路**。`tools/verify-buy.mjs` 開兩個獨立的瀏覽器驗過這件事：同一個時槽的待機段，兩邊算出來的座標到小數點都一樣。

### 鄰居規則為什麼看「無規則鏈」

「1000m 內有另一隻就往反方向走」如果讓 A 的鏈去讀 B 的鏈、B 又讀 A，就變成互相依賴的耦合系統，晚進來的人得把所有 NPC 的歷史一起重播。所以 A 讀的是 B 的**無規則鏈**（同一組亂數，只是不套這條規則）——那仍然是純函式 `f(seed, 編號, k)`，誰都能單獨算。這條規則本來就極少開火（家與家相距 2000m，要隨機漫步一兩個小時才可能靠近到 1000m），這個近似看不出差別。

### 只走回得來的路

隨機漫步遲早會掉進爬不出來的坑——蹬牆井的井底就是：它有地板，但四周只有上不去的細柱。所以每一個候選落腳點都要**雙向**都跳得到才列入。同理，一隻 NPC 的「家」不是牠那一段正中間最近的那塊板子，而是最近的、**至少有三個地方去得了**的那塊。

### 貓出現的那一幀不能掉幀

重播兩千個時槽這件事，最糟的時機正好是「貓出現」的那一幀——玩家看到的就是貓一冒出來畫面就頓一下。三件事把它壓下去：

- **候選點記起來**：一條鏈走的是同一小塊地形上的同幾個點（那是一個很小的圖上的隨機漫步）。每一槽都重掃一次地形是白費的，所以照落腳點記。地形只會往後長、長出來就不再變，所以這份答案永遠有效。
- **每一幀只給一點預算**：`NPC.catchup` 個時槽（預設 300），用完下一幀繼續。貓晚 0.1 秒出現沒有人看得出來，掉一幀所有人都看得出來。預算是整個池子共用的——真鏈每走一步都要問鄰居「你那一槽在哪」，分開記的話這條隱藏的路會繞過限制。
- **柱頂計畫算過就記住**：同一段躍遷會一再重複，而它是這裡面唯一貴的東西（要解彈道還要用真物理預演）。搜尋本身也剪過枝：落點對按壓時間是單調的，所以有效區間用二分找，不必把七種速度乘六十段按壓全模擬一遍。

`npm run verify:perf` 驗的是**每一幀的工作量上限**，不是碼錶——碼錶量到的是那台機器當下在忙什麼。實測（機器沒有別的負載時）最慢一幀 0.9ms。

### 柱頂那一跳

機器人的腦不會瞄柱頂：`nextLanding` 直接略過 `h>=60` 的方塊（那是要蹬的牆），`obstacleAhead` 更把它當成要跨過去的障礙。但柱頂站得住，所以 `npc.js` 自己解一次彈道：用多快的速度跑、按住幾格、從哪一點起跳；站在細柱上沒有助跑空間時改成原地跳，水平距離全靠空中加速補。解析式的彈道看不見半路上的東西，所以最後一關是用**真的物理預演一遍**，站得上去才算數。

## 架構：三層，彼此不知道對方存在

```
┌──────────────────────────────────────────────────────┐
│  <canvas id="fx">     WebGL2，即時 3D                  │
│    貓（三階調著色 + 翻面外殼墨線）                       │
├──────────────────────────────────────────────────────┤
│  <canvas id="game">   Canvas 2D，透明                  │
│    平台 · 地刺 · 金幣 · 草花 · 蝴蝶螢火蟲 · 名牌           │
├──────────────────────────────────────────────────────┤
│  <canvas id="bg">     WebGL2，一支 fragment shader      │
│    天空 · 星 · 日月 · 地平線輝光 · 四層山 · 雨雪 · dither  │
└──────────────────────────────────────────────────────┘
     三張畫布之間沒有資料流，只是各自讀同一個 seed 和同一個 sky
```

背景成本是 **O(像素)**，跟畫面上有多少變化完全無關——這正是想要「隨機多元性」時該站的那一邊。中間層維持 Canvas 2D，所以物理、碰撞、網路一行都沒動。

**降級路徑**：`gl/background.js` 載不起來、或 context lost，`render.js` 裡有一套等價的 Canvas 2D 備援（同樣的天空色帶、同樣四層山、同樣的空氣透視，省掉星星與天氣）。網址加 `?nogl=1` 可以強制走備援對照。

我們也因此躲掉 AETHER 最麻煩的問題：`terrain.js` 得把同一套高度函式維護在 JS 和 GLSL 兩份（他們的解法是從 JS 資料表*生成* GLSL 字串）。我們的背景不參與碰撞，所以永遠不會有兩份真相。

## 本機開發

```bash
npm install
npx wrangler dev
```

http://localhost:8787 — 靜態檔案和 WebSocket 都由這個 port 提供，跟線上一樣。開兩個分頁就能測多人（同一個 `?room=`）。

## 部署

```bash
npx wrangler login
npx wrangler deploy
```

輸出的網址直接能玩，**不需要任何額外設定**。

> **唯一容易踩的坑**：`wrangler.toml` 的 migration 用 `new_sqlite_classes` 而不是 `new_classes`。
> 免費方案只支援 SQLite backend 的 Durable Object，寫錯會部署失敗。

`.github/workflows/deploy.yml` 已經寫好：push 到 `main` 會先跑地形驗證，通過才部署。需要在 repo Secrets 加 `CLOUDFLARE_API_TOKEN`。

## 玩法

| 操作 | 按鍵 |
|---|---|
| 移動 | `←` `→` 或 `A` `D` |
| 跳（可二段跳） | `空白鍵` / `W` / `↑` |
| 蹬牆 | 貼著高牆時按跳 |
| 重新開始 | `R` |
| 手把操作開關 | `G` |
| 左右對調操作元件 | `H` |

**觸控**：預設是水球手勢——按住畫面左右拖曳移動，手指甩出水球就是跳，整個畫面都是操作區、沒有按鈕。

**手把操作**（開始選單「開始跑」下方的〈操作設定〉，預設收起、手把預設關閉）：改成兩側固定操作列，一側搖桿一側跳躍鍵。開啟時所有儀表板會用 FLIP 動畫飛進操作列上半段（上儀表板、下操作元件），中央整片留給遊戲，相機取景也跟著往乾淨區的中心讓；水球則整個關掉，中央連指標事件都不收。直向手機自動改成上下介面：上帶儀表板、下帶操作元件。開關旁的分段膠囊可以左右對調操作元件，兩者會橫向交換飛過去。設定會記在 `localStorage`。

**儀表板**：左側只有公尺、個人最佳、金幣三格（速度和時刻不再上儀表板，天氣也是——它們照樣在跑，只是不佔位置）。手把模式下這三格改成直的一疊，由上而下是個人最佳、公尺、金幣（順序用 CSS `order` 排，DOM 沒動）；直向的上帶最矮只有 104px，所以那三格會變成數字和標籤同一行的窄條，不會掉出橫帶。右側常駐房名（底色就是連線狀態）加延遲，空間夠就並列同一行，還有即時排名；其餘（連線文字、在線人數、地形 seed、本房紀錄、複製連結／換新地形）收進可展開的「更多」，手把模式預設收起，展開就直接接在排名下面——第一排釘住，底下整段是同一個捲動區，不是另外掛一段自己會捲的東西，也沒有漸層陰影。直向展開時面板還會往下長成浮在遊戲上的面板（下界停在操作元件之前）。房間人數超過兩個人時「換新地形」本來就按不動，按鈕會直接捲出去把位置讓給「複製房間連結」。

**買重生點**：地圖上每 2000m 住著一隻旅貓。**站著不動**、走到牠身邊點牠一下，牠會冒出購買邀請，再點一次成交（第 1 隻 50 枚金幣、第 2 隻 150、第 3 隻起 300）。買下來之後牠就在那塊板子上定居、不再遠行，那塊板子的正中央就是你的重生點——摔死之後從那裡重新開始，里程也從那裡算起。金幣死掉不會歸零，同一個房間、同一個名字會一直累積。

必須靜止才點得到是刻意的：跑動中的誤觸如果被當成「跟貓講話」，那一次左右操作就被偷走了。

**分房間**：網址加 `?room=名字`。同房間的人才會互相看到，也才共用同一份地形、同一個時刻、同一種天氣、同一份排行榜。

**其他參數**：`?solo=1` 強制單機；`?nogl=1` 強制 Canvas 2D 備援；`?server=wss://...` 連別的 Worker。

## 免費額度

| 項目 | 免費額度 | 這個遊戲怎麼吃 |
|---|---|---|
| **靜態檔案請求** | **免費、不計數** | 進遊戲、載 JS、載 `cat.bin` 都不算 |
| Worker 請求數 | 100,000 / 天 | WebSocket 收到的訊息以 20:1 折算，10Hz × 1 人 ≈ 每小時 1,800 次 |
| DO 運算時間 | 13,000 GB-s / 天 | 一間房開著約每小時 0.45 GB-s |
| SQLite 儲存 | 5 GB | 每房一個 seed + 世界時鐘 + 10 筆排行榜 + 重生點與錢包 |
| **NPC** | — | **零**。位置是世界時間的函式，沒有任何逐幀封包，只有成交時一則訊息 |

約每天 55 人-小時。額度用完不扣錢，只會回錯誤（前端顯示「離線（重連中）」並繼續單機遊玩）。

`cat.bin` 走靜態檔案通道，不吃 Worker 額度。貓是每幀即時算的，成本在 GPU 不在 Worker。

## 調參數

### 手感

`public/src/constants.js` 的 `PHYS`。改完跑一次驗證：

```bash
npm run verify
```

```
幾何檢查：✓ 全部通過  (120 個 seed)
機器人試跑：目標 6000m
  跑完全程：120/120
```

用彈道公式驗算每個空隙都在單次跳躍射程內，再用**同一套** `player.js` 物理跑一隻只會按左右+跳的 bot。地形生成器本身照著 `PHYS` 反推可通過距離上限，所以改物理參數，關卡難度自動跟著調整。CI 也會跑。

### 外觀

- 顏色：`gfx/daycycle.js`（光與天空）、`render.js` 的 `ALB`（世界的 albedo）、`gfx/decor.js` 的 `PETALS`。
- **顏色一律是 linear**，經過 `shade()` 打光、`acesTone()` 落地。直接把這些數字當 CSS 顏色會又亮又灰——常數是為「ACES 套在 linear × 1.25、不做 sRGB 編碼」校準的。
- 山：`gl/background.js` 的 `R_PLX / R_SCALE / R_AMP / R_HAZE / R_ALB`，備援那份在 `render.js` 的 `RIDGE`（兩邊要一起改）。
- 裝飾密度：`gfx/decor.js` 的 `MAX_BLADES` / `MAX_FLOWERS` / `MAX_CREATURES`、`gfx/tree.js` 的 `MAX_TREES` / `MAX_SEGS` / `MAX_TUFTS`（Canvas 2D 是 O(數量)，一定要有硬上限）。

### 蟲

`gfx/decor.js` 的 `drawBugs`。牠們**繞著花叢飛，不是繞著空地**——用的是同一組 clump 雜湊，所以蟲一定在花上面。這是原專案花很多篇幅講的事：另外做一組散佈會讓蝴蝶在離花一公尺的裸草上盤旋，而「眼睛會注意到差一點，卻不會注意到根本沒有」。

飛行是**脈衝響應的和**，不是正弦。正弦沒有蟲的兩個特徵：沒有轉角，而且在時間上是對稱的。每個「踢」在 `s(0)=0, s'(0)=1` 起步——那個速度不連續就是轉角——在 `s(L)=s'(L)=0` 結束，所以它離開視窗時已經淡完，迴圈可以硬性截在 4 次而且不會跳。朝向是解析導數，所以完全不需要保存前一幀的狀態，跟其他裝飾一樣是無狀態的。

螢火蟲的閃是**亮度的責任週期**（`pow(sin, 4.5)`），不是均勻的一閃一閃：大部分時間接近 0，只有短短一下衝到 1。那個不對稱才是螢火蟲。用 `lighter` 加色混合畫兩圈——外圈的暈加核心。

### 樹

`gfx/tree.js`。五個物種共用同一份骨架程式，差別只在 `SPECIES` 的參數：`leader` 決定有沒有一根主幹到頂，`droop` 決定側枝往上開還是往下垂，`tuftN` 決定樹冠多密。骨架用深度優先展開，每個節點的亂數 salt 從 `k = 父 k×4 + 子序號` 推出來——所以同一棵樹每幀長得一模一樣，而且跟草花一樣不必存任何東西。

**每 1000 m 換一季，同一段裡只有一類樹**（`SEASON_SPAN`、`SEASONS`）：

| 距離 | 林相 | 物種 |
| --- | --- | --- |
| 0–1000 m | 綠 | 闊葉 + 針葉 |
| 1000–2000 m | 秋 | 只有闊葉，暖色 |
| 2000–3000 m | 冬 | 積雪的針葉，或落光了的枯枝 |

之後照這個順序循環。分界只看樹自己的 x，所以跟其他東西一樣是無狀態的：不必記「現在是第幾季」，鏡頭往回拉看到的還是同一片林子。整片一起換比逐棵抽籤有力得多——一致性讀起來像地理，隨機讀起來像雜訊。

冬樹的雪不是另外畫上去的圖層：葉團的三個色階本來就是**照高度**分的（高的亮），所以把色階從暗綠壓到白之後，雪自然堆在朝天的那一面。枯枝那種把 `tuftFlat` 壓到 0.42，雪就是躺在枝上的一條，不是掛在枝上的一球。

**樹冠掛在末梢，不是撒在外框裡。** 另外做一組散佈遠看很像，一走近就會看到葉子浮在沒有枝的空中，跟蝴蝶不繞著花叢飛是同一個錯。

**風只讀慢項。** `field.js` 把風拆成可分離的兩道波就是為了這裡：快項波長 4.1 單位比樹幹本身還細，樹幹讀了只會發抖，所以樹幹只讀 `slowGust`，葉團才加上 `gust` 的快項當抖動。彎曲量是 `u²`（懸臂樑的形狀，根部不動、往上愈彎），相位隨高度延遲 0.16 秒，樹梢因此比根部慢半拍——那個時間差就是整棵樹的鞭子感。

**不用 `edgeFade`。** 草進出視野時縮小沒人看得出來，一棵樹忽然矮一截很明顯；改成把採集範圍往兩側各推 `MARGIN`，樹在畫面外就已經是完整的。同理，額度不夠時是整棵不長（`SEG_RESERVE`），不會出現半棵樹。

樹畫在**平台之前**，所以板子會擋住樹冠、樹退到關卡後面。這是遊戲性的決定：一棵擋在路線上的樹會讓玩家看不見下一塊板子。

### NPC

`public/src/npc.js` 的 `NPC`：`spacingM`（每幾公尺一隻）、`slot`／`move`（時槽長度與其中的移動窗口）、`span`／`reach`（找落腳點與一次躍遷的距離上限）、`talkPx`（要多靠近才點得到）、`prices`（價格表，改了要一起改 `worker/index.js` 的 `PRICES`）。改完跑：

```bash
npm run verify:npc
```

```
  同步：早進與晚進的人最大差距 0.000000px
  躍遷：3312 段，其中 68 段沒走到（2.05%）
```

「沒走到」是指那一段在移動窗口內沒站上目標——時槽結束時會被對齊回去，所以看得到的只是偶爾一次比較硬的落地。這個數字爬上去就代表 `reach` 或 `move` 不成比例了。

### 地形

`public/src/level.js`。七種段落：平地、階梯、柱子連跳、大斷崖、地刺區、高空路線、翻牆。新花樣加在 `step()` 的機率表，用 `this.place(gap, dy, w)` 放平台——它會自動把空隙夾到跳得過去的範圍內。

## 已知限制

- **沒有防作弊**。分數是前端回報的。
- **一間房上限 12 人**。單一 Durable Object 有約每秒 1,000 次請求的軟上限。
- 地形是靜態的（沒有移動平台），因為那需要同步時鐘。
- 幽靈玩家的位置有約 120ms 的插值延遲，這是刻意的，換來平滑移動。
- 貓的 `wall` 姿勢是「後仰」而不是真的貼牆。
- 40 px 下轉身讀得到但很細微，線索是輪廓變窄與尾巴換邊，不是臉。
- 轉身時 `turnRate` 全程飽和（14 rad/s 對上 3.2 的參考值），所以身體的傾斜沒有自己的動態。
- 角色層關掉了 alpha blending：半透明的幽靈疊在另一隻幽靈前面時會蓋掉它而不是透出來。開 blending 的話不透明網格會自己跟自己疊加（0.58 的幽靈在耳朵和臉頰交界處會變成 0.82），要修得多畫一次 depth prepass，不划算。
- 背景層在直式手機（視野高達 1300 個世界單位）會把地平線推到畫面 35%，那個構圖比橫式暗很多。
- NPC 的位置在**待機段**（每 6 秒裡的 4 秒）是逐位元一致的，移動中的那 2 秒各算各的，可能差幾 px。誤差不會累積：每一槽結束都會收斂回落腳點。
- NPC 不會二段跳也不會蹬牆，所以蹬牆井裡的細柱牠上不去（那本來就是設計給蹬牆的）——牠會自己不選那些落腳點。站在地板上的矮牆柱頂則跳得上去。
- 房間開超過 3.3 小時，NPC 的行為鏈會重新錨定一次（等於瞬移回家）。這是為了讓晚進來的人不必重播四萬個時槽。
- 重生後地圖上的金幣會重置，所以「故意去死、重撿同一片金幣」是刷得起來的。價格表就是照這個前提訂的。
- 買家是用**名字**認的（伺服器只有名字，連線 id 每次都變）：同名就是同一個人，改名字就找不回自己的重生點。
- 蝴蝶與螢火蟲的動畫吃的是各自客戶端的牆鐘，所以不同玩家看到的蟲不在同一個位置。花叢本身是同步的（座標雜湊），蟲只是裝飾，沒有為它多傳資料。

## 疑難排解

| 症狀 | 可能原因 |
|---|---|
| `wrangler deploy` 說 Durable Object 需要付費方案 | migration 要用 `new_sqlite_classes` |
| 角色是方塊不是貓 | 這台裝置沒有 WebGL2，或 `assets/cat.bin` 沒被部署到 |
| 背景很陽春（沒有星星和天氣） | 走了 Canvas 2D 備援。看 console 有沒有 WebGL 錯誤，或網址是不是有 `?nogl=1` |
| 「離線（重連中）」一直閃 | 當日免費額度用完，或 Worker 部署失敗（`npx wrangler tail` 看 log） |
| 兩個人的地形/天色不一樣 | 兩邊的 `?room=` 不同 |
